General rules (apply to every stage)

G2. Not finding something where you looked does not prove it is absent. Write "not found in what I examined" or "confirmed absent", and say what you searched.

- A "-abc1234" suffix on a method name is Kotlin value-class mangling: drop it.
- A class name ending in a dollar sign and a number, or containing "lambda" or "ExternalSyntheticLambda", or a method named invokeSuspend, is a compiler-generated lambda or coroutine. Resolve it to the one function in the outer class that uses the reported API. If the outer class never names that API, resolve it to the one function it calls, in the same Gradle module, whose body uses it. If several candidates qualify, take the one that holds the value RVSec reported as a literal. If the value is passed in from elsewhere, say that the location is uncertain.
- A method missing from the file may be declared in another file of the same package. A Kotlin type or object may be declared in a file with a different name: search for its declaration, not only for a file named after it.
- In a Kotlin Multiplatform project, the report comes from the Android build. Use the androidMain, main or flavour implementation, never the desktop, JVM, iOS or JS one.

Stage 3. Facts and decision
3.1. First write a numbered Facts list containing only what the code and the sources establish, each fact with its source and status. Write it before any decision, and keep it separate. Then decide only from those facts and cite their numbers. Treat your own earlier summaries as interpretation, not evidence.
3.2. Write each requirement of the rule as a positive statement, for example "the iteration count is at least the minimum", never as the violation. Mark it holds, does not hold or undecided, and say which part of the rule it comes from (order, argument value, value another rule must produce, forbidden call). For an undecided requirement, give one of three reasons: the source does not show it, it lies outside what you examined, or only run time decides it. Whether the checker models it or would notice it is never a reason. If the source settles it, decide it.
3.3. After the Facts, list the evidence you are missing. For each item, say whether reading the repository can answer it or only running the app can. Do one focused follow-up search for the repository items, add what you find to the Facts, and list what you looked for and did not find, with the reason. A question only a running app can answer stays open. That RVSec's exploration did not execute a method means it was not reached in that run, not that it never runs.
3.4. Who the code serves. Say:
- in one sentence, what the reported code is for and which callers reach it;
- who is on the other side: a third-party service, a peer the user operates, the same app or device, or unknown;
- when it runs: always, behind a user option, behind a build flag, or unknown.
Claim that the other side depends on the weak behaviour only when repository code other than the reported code and the rule shows that it cannot meet the rule: another connection to the same peer accepted by a fingerprint or pin, a self-signed test fixture, a fixed protocol. Quote up to three passages of at most 400 characters verbatim. Permissive code by itself shows nothing. This reading never decides whether the violation is real.
3.5. Answer the questions for the API's kind:
- TLS: which protocols are enabled, which are negotiated, and whether the context is a negotiating one.
- Digest: what the hash is used for (security, cache, identifier, runtime discriminator, external contract), where the expected value comes from, who else computes or compares it, and whether a change on the client alone is safe.
- Cipher: the transformation, the initialisation, the nonce lifecycle (reuse), authentication and key provenance, each judged separately.
- Key generation: the algorithm, the provider, the initialisation arguments, the key size and who consumes the key.
- Dependency: the artifact, its version, the fix or replacement, the migration and compatibility.
3.6. Rules by kind:
- General: an Android component declared android:exported="false", or guarded by a permission the caller must hold, cannot be invoked by another app, so its input is not attacker-controlled on that basis alone. Look in the target source for a defence before you report its absence: a guard already present answers the question.
- TLS:
  - Do not infer legacy protocol negotiation from SSLContext.getInstance("TLS").
  - Never weaken trust management, certificate validation or hostname verification.
  - Do not pin a single version: a TLSv1.2 context leaves TLS 1.3 off on Android. Keep a negotiating context ("TLS" in place of "SSL" gives the same context) and restrict versions, if at all, on the socket.
  - An assignment to a copy of the parameters has no effect (getDefaultSSLParameters returns a new object). The honest fix removes it rather than changing its value.
- Digest:
  - When the expected value is compared by the project's own backend, which would have to accept a new value, a client patch that keeps the old value working during a rollout is allowed. Its PR states the rollout: the backend must accept the new value first and keep the old one until older clients are gone. A third party's or a public API's fixed value is an external contract (3.17).
  - Classify the usage before judging impact. An equality comparison alone does not mean the hash protects integrity against an attacker.
  - Do not replace a client digest when the expected value is an unchanged external contract. A cache key, a runtime discriminator, a persisted identifier and a security digest each need different migration evidence.
  - A hash that names stored data or leaves the app is a persistence or protocol value, not a cache key.
  - Before you change a hash algorithm, check who else computes or compares the value. If a server, a stored file name or another repository depends on it, the change needs a migration or cannot be made on the client alone.
  - A digest used only to tell runtime variants apart is replaced by explicit variant logic that keeps every known mapping, not by a different algorithm.
- Cipher: changing only the transformation is not enough when an initialised Cipher or a nonce is reused. Never introduce a constant key, IV or nonce.
- Key generation: do not infer an invalid key size without an exact argument.
3.7. Give five separate judgements:
(a) cause in the code: confirmed, inferred or unknown;
(b) reported rule broken: confirmed, established from source even though RVSec gave no usable message, not confirmed, or unknown;
(c) security impact in this app: confirmed, not established, no security impact, or unknown;
(d) compatibility of a change: preserved, regression risk, or unknown;
(e) scope of what the change touches: complete, incomplete, or not applicable.
Keep "is the checker right" apart from "does it matter", and "can a patch be written" apart from "should it be sent".
3.8. If the code shows the call the rule matches, on the object it tracks, with the required condition failing, the violation is confirmed. An absence counts when you searched the whole relevant scope. Do not ask for a run of the program to prove what the source decides; RVSec's report is the second, independent signal.
3.9. Explain what was reported, nothing more. For a call-order report, the cause is about the order of calls; for an argument report, it is about the argument's value. A cause from another part of the rule is recorded as a separate requirement. Do not fold other requirements of the rule, which RVSec did not report at this spot, into the cause or the change. Explaining away the reported condition says nothing about the rule's other requirements. If the code clearly breaks another one (a hard-coded keystore password, say), record it separately; 3.31 says when the maintainers hear about it.
3.10. When RVSec's message reads "expecting one of X but found Y", the list X decides what it accepts, above any rule text found elsewhere. A value in that list is accepted, so do not hold back or question a fix that uses one. Each report's list applies only to its own call. When RVSec's message says it does not accept what the code does, an alternative that only the published rule text allows does not make the report wrong. This does not apply to a report that no producer of a value was observed; decide that one from where the code gets the value.
3.11. If RVSec gave no usable message, that is a limit of the report, not a fact about the code. If the source alone proves the violation, go on, and say in the text that the report itself could not be corroborated.
3.12. Constant material. Key, IV, salt or seed bytes built from something compiled into the app (a literal, a resource, a BuildConfig field, a constant, an array nothing fills) are the same in every install and readable from the APK. They break any requirement for random or generated material, unless the code reads those bytes back from the data it is processing. Do not ask what the constant holds or whether it was once generated at random. Whether fixed material is a real weakness in this design (a fixed IV under a key that is never reused) is the impact question.
3.13. Predictable generators. Key, IV, nonce, salt or seed bytes from java.util.Random, kotlin.random, Math.random, or anything seeded from time, a counter or a constant break a randomness requirement, however random they look. Only SecureRandom or a value the provider generates meets it. Whether that matters here is the impact question, never a reason to call the report wrong.
3.14. Provider-generated IV. Suppose encryption calls Cipher.init with no IV, keeps cipher.getIV() with the ciphertext, and decryption reads it back. Then the IV is random at its origin, and RVSec simply cannot trace it. Do not block on the unknown producer, and do not make the code supply its own encryption IV (an AndroidKeyStore key refuses that). Decide the outcome by the other rules; 8.6 says how the unit ends when every draft would replace the provider's IV.
3.15. The bar for "false positive" is very high. Say the report is wrong only when it is close to absurd that it is real, and only on confirmed facts read from this repository's code or from the rule itself, never on RVSec's message or on web pages alone. If you cannot show that, the answer is "undecided", not "false positive". Further limits on dismissals:
- Never dismiss a report because the code resembles a known false-positive category (an AndroidKeyStore key, a custom trust manager).
- A list of "known false positives" found on the web, or not checked against the rule, never supports a dismissal. That includes the rule's own list of possible false-positive shapes given at the end of this block: it was never reviewed against the rule. When the code matches one of those shapes and literally breaks the rule, the violation is confirmed without security impact (then 3.18 or 3.20 may apply); when it does not literally break the rule, judge from the evidence as for any report.
- Code that matches the rule's own list of violations without a security stake is not a false positive: the violation is confirmed without security impact, and you still propose the change when one keeps what every consumer of the value relies on, unless an external contract fixes the value.
- A documented false-positive case of the rule applies only when the code really has the property the case describes, read from the code, not by resemblance.
- A case about what static analysis cannot see is not matched by a value RVSec measured at run time. One fingerprint across runs for material that should be random is the forbidden constant.
- An IV computed from constants or from the key is not an IV read from the stored ciphertext.
- Code that breaks the rule's letter in a harmless context is a confirmed violation without security impact.
3.16. Rule overmatch. Suppose the rule matches any method with that name, without constraining the receiver type or the parameters, and the code's call plainly cannot be the governed API (a different declaring class, or arguments the governed method does not take). Then RVSec matched the wrong method: the violation is not confirmed, quote the rule's matching clause, and propose nothing.
3.17. A harmless explanation dismisses a report only where no rule-compliant change keeps the behaviour. If a compliant form exists that everything consuming the value still accepts, the violation is real (perhaps harmless) and should be fixed. If an outside protocol, server or file format dictates the value, the violation is real but that external contract prevents the change; it is still not a false positive.
3.18. Null or omitted argument that selects the platform default. If an explicit call yields exactly the same default object by the path the platform documents, propose that explicit form as a small rule-only change. The explicit form must not hand a null default to another checked API, and must not just move the default to another governed call. If no explicit form yields the identical object, the code is the documented use: the violation is real, there is no safe fix and no security impact, and nothing is sent. Example: a TrustManagerFactory initialised with a null KeyStore applies platform configuration.
3.19. A hash algorithm that a public standard the app implements dictates, computed where the standard defines it, protects nothing the app chose and cannot change without breaking every peer. Example: SHA-1 in the WebSocket Sec-WebSocket-Accept header under RFC 6455. Write NO_ACTION.md naming the standard and section. This does not cover signatures, MACs, or fingerprints, identifiers and checksums whose algorithm the app or its own server picked.
3.20. Documented correct use. The code may already use the API exactly as its documentation prescribes, with every change that would satisfy the rule altering what the code trusts, accepts or protects. Cite the documentation; there is nothing to fix. A change that only passes a null default to another checked API does not count as such a change. This ends in NO_ACTION.md only when there is no security impact. If the violation weakens security, the maintainers are told (ISSUE.md).
3.21. Deliberate insecurity. A suppression, a comment or a gate showing that the behaviour is deliberate never makes the report false. It shapes the fix:
- If the behaviour runs for everyone and users may rely on it (self-signed home servers, IP addresses), do not simply remove it. Consider "no safe fix" with an issue that proposes an opt-in setting or certificate pinning, or keep the old behaviour behind an option only if such an option already exists. Never invent a new setting.
- If an existing option turns it on, keep that path working and change only what runs when the option is off.
- If a debug-only build flag gates it, release builds are unaffected; say so.
- A documented reason for one usage does not automatically cover another.
3.22. Hardening towards peers. No longer offering to, or accepting from, a server or peer an old protocol, a weak algorithm or an unverified certificate is hardening for the maintainer to review. It is never by itself a reason for no fix or an empty plan. It breaks someone only if the repository shows a dependent:
- who the code serves, established with quotes (3.4);
- signs that the behaviour is deliberate and unconditional (3.21);
- an option in the code that turns it on;
- other code that handles the same peer in a way the stricter behaviour would refuse (a pin, a self-signed certificate);
- this repository's maintainers saying such peers are supported.
A peer you would have to assume is not evidence. Without a dependent, make the change and leave the question as a note.
3.23. Stored data. Before saying a change breaks stored data, read the code that writes it and the code that reads it back.
- A self-describing record, one that carries the setting it was written with and whose reader uses that setting, needs no migration.
- The readers you listed are the readers; only a reader outside what you examined remains an open question.
- A value written under a key that nothing reads breaks no earlier data, and its compatibility is no reason for no fix, an issue or a regression.
- If the value leaves the app (clipboard, share, file, network), other installs, possibly older ones, read it. A format change is then a note for the pull request. It blocks only if the same app version could no longer read the value.
3.24. External contracts. When every caller of a method, constructor or field is in this repository, changing its signature or name and updating the callers in the same patch is ordinary repair, never a reason for no safe fix. Only what code outside the repository calls or reads can prevent the change: a published library API, a framework callback, an exported component, a server, a protocol, a stored format. If examining every reachable caller found no outside consumer, that supports the change.
3.25. Library code. For a report inside a library, assume the rule reached code it does not model, unless an advisory, the library's changelog or a fix commit says this version is defective and a later one is not. With such an authority, bump the declared version of a direct dependency, or upgrade the parent of a transitive one. Never force a transitive version on its own.
3.26. Size and concurrency affect impact only. A method that accepts only one fixed input size cannot suffer a weakness that needs longer or repeated input. A final field with one writer, called from one site you examined completely, cannot race. In both cases the violation itself still stands.
3.27. Impact is decided separately from repair. A confirmed violation without security impact here still gets a pull request when a correct change exists. That includes a small rule-only change that alters the value the checker sees, such as "SSL" to "TLS" or an explicit default. Low impact is never a reason to hold back the fix.
3.28. Hold back a patch only when you cannot write the change: the cause is not established, code you need is missing, or it is unclear which file to change. Everything else is a note in the pull request:
- Any question that a maintainer, a device, a server or data from older versions must answer becomes a note in the pull request saying what the reviewer should check. That covers whether RVSec will accept the change and whether a name may change.
- For each concern, ask whether your build would reveal it. What it cannot reveal (a server, a device, data from older versions, the checker's acceptance, a maintainer's choice) stays a stated open point.
- If the cause and the violation are confirmed and only compatibility is uncertain, still write the patch.
- If you could not check every consumer of the changed value, still propose the change, and list in the pull request the consumers and storage locations the reviewer should check.
- That the replacement code does not exist yet is not missing evidence: writing it is the job. Something only a device can show is a note for the reviewer, never a reason to withhold the change.
3.29. RVSec saw the reported call run in this app. Unless you established that the report is wrong, missing evidence about where a value comes from, or about which file to change, is not a reason to send nothing:
- First search the repository for exactly what you said was missing, and decide again with what you find.
- If it is still missing, propose the change and say in the pull request what you could not confirm.
- Do not stop on a question that reading the code answers: which class a call binds to, which dependency ships a class, whether the governed call is there, who calls the method.
3.30. Treat all the reports listed above as one unit, with one cause, one decision and one patch. They sit in one piece of code: the same method under two rules, one method calling the other, one object's lifecycle reported at several steps, or a value one method stores and another reads back; check these links yourself.
- If at least one report can be fixed, the unit gets the fix. Name any report that no safe change resolves (a gap in what RVSec could trace, missing evidence) and leave its code exactly as it was.
- If a report exists only because the object it uses came from another reported call (a key built by a flagged method), its cause is that producer: fix the producer.
3.31. Choose the outcome:
- PR.md, when a correct change exists, whatever the impact (3.27), and the violation is confirmed or established from source, with its cause confirmed. Under 3.29, a reported violation you have not shown to be wrong also counts.
- ISSUE.md when (a) the violation's cause is confirmed and grounded in this repository's code, and either (b1) you stopped before any draft (no safe fix, no edit found in stage 4, an external contract) and its security impact here is confirmed, or (b2) the drafts ran out under 8.8(d) and either the violation (or its security impact) is confirmed, or you judged neither "report not confirmed" nor "no security impact". Also use ISSUE.md for another requirement of the same rule that the source clearly breaks (3.9), when the unit gets no pull request and that requirement plainly matters for security.
- Library code: a defect that belongs to a library is an ISSUE.md for that library's repository (name the repository in the first sentence) when the ISSUE conditions hold; otherwise NO_ACTION.md with the reason that applies.
- NO_ACTION.md, otherwise. Give one of these reasons; the words before its colon are its name:
  - violation without security impact: documented correct use (3.20), a value a standard fixes (3.19), a provider-generated IV (8.6), or every possible change only hides the call from the checker (4.6, 8.8);
  - confirmed violation without a safe correction: impact not confirmed;
  - an external contract prevents the correction: impact not confirmed;
  - report not confirmed: a false positive under 3.15 or 3.16;
  - undecided: insufficient evidence after 3.29;
  - correction not generated: you could not write a correct, building patch (8.8, 9.3).
3.32. The maintainer responses at the end of this block are evidence, never a verdict:
- Weigh their technical reasons, for example that a provider-generated value is secure, or that a checksum is compared across releases.
- Count only what human maintainers said, not review bots.
- An answer about contribution policy (not accepting pull requests, a CLA, no AI contributions) says nothing about the change. Such a policy in this repository is not a reason to stop either.
- Shape your change so that the objection they raised would not apply: keep a deliberate behaviour behind an existing setting or a debug-only condition; do not change a checksum persisted or compared across processes or releases (one recomputed in the process on both sides may change).
- These responses say nothing about whether this report is real.
3.33. A rename is never a reason to hold back a change. Do it correctly (every reference updated, the build passing), or add a correctly named function and switch the callers to it. A maintainer's preference about a name is at most a note.
3.34. Before leaving this stage, check your decision against the rules above:
- A pull request needs an established cause, a confirmed (or source-established) violation, and facts you can point to.
- A dismissal needs confirmed facts from the repository or the rule (3.15).
- If the decision fails a rule, fix it using only the facts you established. Do not soften a cause or a violation that is genuinely unestablished just to pass.
3.35. If you judged the current code to be documented correct use (3.20) but still found a change worth proposing, make a single attempt at it (8.7).

Stage 4. Plan (only if stage 3 chose PR.md)
4.1. Make a plan:
- required edits: file, symbol, what changes, why, and the fact (file:line) behind each edit;
- required tests, or "no test" and why;
- behavioural invariants: what must keep working, including the first-run path and the existing-data path, every read site of a stored value, and each reader you listed;
- forbidden changes.
A plan for a change you decided on has at least one concrete edit. If you then find that no edit works, write down each edit you considered and exactly what rules it out, and go back to the outcome rules of 3.31. Never stop with no edit and no reason.
4.2. Plan edits only to files you have read in full. The only new file you may create is a test inside the unit-test source set of the same module as the code you change (commonTest for commonMain). If that module has no unit-test source set, plan no test.
4.3. Change only the values the report is about, that is, those its message names or rejects. Add only what that change needs to compile, to keep existing data readable, or to keep a joined report resolved.
- Leave every other argument of the reported call as it is (iteration counts, key or tag sizes, salts, modes), even where a stronger value looks better.
- Write the new value where the old one was: a literal stays a literal, and an existing constant is changed in place.
- Add a constant only when the same value is needed in more than one place you change.
- Prefer the smallest change that satisfies the reported check.
4.4. Every production edit must change exactly what the report checks: the value, where it comes from, or the call it names. Do not fix a different requirement of the same rule instead. For each joined report, change something its checker sees at its own call: a different call, object, value or order. If nothing like that fixes a report, do not touch its code at all: no value moved into a local, no split statements, no extracted helper.
4.5. No conditional edits ("only if a trace shows...", "skip this if..."). Decide now from what you have read, then either plan the edit or leave the file alone.
4.6. RVSec is a runtime checker. It sees each call, the object it is made on and the values passed, never the source text.
- These change nothing it sees, so they cannot satisfy its rule: inlining or extracting a helper, passing an object's parts one by one, splitting or merging statements, renaming or retyping locals.
- Never hide the checked call from the checker while the app still holds, trusts and does the same thing: no factory, provider or SPI written around the same object; no key class of your own over the same bytes; no holder of your own (data class, record, Pair, Map, list or array) carrying the same parts from the same sources; no other library or lower-level API producing the same value.
- A real fix changes what the governed call receives, takes it from the platform, or adds, removes or reorders the calls the rule governs.
- Using an object the platform already returns, or changing what the parts are or where they come from, is a real change.
4.7. Several reports in the same code get one change, never two incompatible rewrites. A neighbouring report you concluded needs no change stays as it is, unless your change must touch it (the decrypt side of a format you change in encrypt).
4.8. Every value that contributed to the original result (a parameter, a build-time field, an environment value) must still contribute to the new path, unless removing it is the fix itself. Where the rule forbids it in its slot, move it to another argument. Never move a constant into a slot whose rule forbids constants, such as a password or key argument. List each such value among the invariants.
4.9. If the code you change touches a stored value, or an object the app saves whole and reads back (a backup, an export):
- everything saved before must still read;
- plan every reader and writer, so that they agree on the old and the new format, emergency values included;
- migrate a stored verifier only after a successful authentication;
- a value read back after a restore or on another device must not start depending on a key bound to this device.
List those read sites among the invariants.
4.10. If the change alters what a method returns, plan an edit for every constructor parameter, function parameter and property that receives that value with that type.
4.11. Keep existing entry-point names so that callers need no edit, unless the name states the behaviour the patch removes (an algorithm, an encoding, a version). In that case take the first of these that applies:
(1) switch every caller to an existing, correctly named declaration;
(2) otherwise rename the declaration, or its whole overload family, together with every reference, in the same patch;
(3) otherwise add a correctly named function beside it, switch every caller to it, and keep the old one only if callers outside the patch remain.
Never add a helper that no production caller uses, or a method that only delegates to a renamed one.
4.12. When you replace a deprecated API, use the mechanism the repository already uses for the same role, where that mechanism keeps the behaviour. Never build a queue, executor or cancellation scheme by hand on top of a mechanism that lacks it. Keep every behaviour of the old API you listed in 1.20, or name the deviation.
4.13. Tests:
- Plan a test only when the change adds or alters logic that a unit test can observe through the code's own methods: a branch, a parsed value, an error path.
- No test for a plain value swap (algorithm, protocol, mode name, constant), for removing dead code, or for behaviour visible only through the platform, the network or the provider. Record that no test was added, and why.
- A test may import only the repository's own packages, the standard library and the test libraries the module already declares. Never add a test dependency to a build file. If the test you want needs one, write a simpler test or none.
- Do not edit existing tests that the report does not concern.
- If the repository has no test source set, write no test, and mention what a reviewer could check by hand. A missing test never stops the change.
4.14. Never edit a file only to add comments or documentation.
4.15. If an earlier plan in this session failed, do not plan the same thing again (stage 8).

Stage 5. Draft
5.1. Make the planned edits and tests directly in the source files. Draft from the required edits and their reasons. The invariants and forbidden changes are what you check the finished draft against in stage 7.
5.2. Change persisted file formats only as far as the plan's required edits do.
5.3. Edit only the planned files. A planned file may turn out to need no change because it already fits (a caller whose entry point you kept): leave it then, and never change a file just to have an edit. The reported file always needs edits.
5.4. In a build file (a Gradle script, a version catalog), change only the declaration lines the plan names, and keep the file's own style: catalog alias, constant or literal.
5.5. Keep every existing public or protected signature, unless every caller is in this repository and you update them all.
- A function added beside an existing one keeps that function's visibility, never a wider one.
- Kotlin helpers that are not meant as external API are internal or private; never rely on Kotlin's implicit public.
- Rename a local variable or parameter whose name embeds the value the patch removes.
5.6. Keep checked exceptions compilable across changed callers and callees: declare or catch what is now thrown, and drop catches for exceptions no longer thrown. Never let a background task's exception disappear into a Future that nothing reads.
5.7. Where you put a new declaration in the braces fixes its scope; indentation does not. A function or property called unqualified from another file or class must be top-level, outside every class, object or interface body. A nested class not declared inner has no access to the outer class's instance members.
5.8. Call only symbols that exist in the repository, or that this patch adds, with the exact argument count each constructor and method declares. Never assume an overload, a constructor or an inner class that is not declared. Do not keep a whole owner object alive just to replace a cryptographic primitive. Dispose of or wipe a replaced sensitive wrapper before reassigning it.
5.9. Keep every existing comment, commented-out line, licence line and unresolved TODO exactly as and where it was, also inside a block you rewrite. Change or remove a comment only when it describes code you changed, or a TODO you resolved.
5.10. Tests:
- Prefer a package-private seam to reflection.
- Do not call private members, do not read production source text, and do not assert that two constants are equal.
- Never assert equality between two separately constructed values of a type that does not declare equals: assert on their fields or on the same instance instead.
- Write a known expected value in the readable form the project uses, for example the hex or Base64 string the specification publishes, never a long list of byte literals.
- A tamper test asserts the specific authentication-failure cause, and a change to an object's lifecycle should get a dispose test (W2).
- Put a new test in a file named after the class it tests.
- If an existing test file you must use does not compile, fix only the compiler errors it has, using current APIs, and keep the test's intent. No other cleanup.

Stage 6. Checks: run this checklist on your diff (git diff, and git status for new files, each read whole) and record each item as pass or fail
Any failed item from 6.1 to 6.26 fails the draft; go to stage 8. The warnings at the end never fail a draft.
Effect
6.1. The reported call no longer receives the reported value, or its call order or the forbidden call has changed as the report requires. What changed is what the report checks.
6.2. The production edits change more than comments and whitespace.
6.3. No added statement builds or casts a value and then discards it. No governed call was added whose result is unused or whose exceptions are swallowed. No object is constructed only to be thrown away.
6.4. None of these, all of which leave the material unchanged:
- a factory, provider or SPI subclass whose product is the object the code already passed;
- a holder or key class of the app carrying the same parts or the same constant bytes;
- an object rebuilt from its own parts, its own getters or its encoded bytes;
- an entry the code just stored, read back from the same store and alias and repackaged;
- a round trip that hands back what went in (wrap and unwrap, encrypt and decrypt under a fresh key, encode and decode).
6.5. No new path whose catch or fallback, for a missing algorithm, provider or class, reaches the original value (or another name for it) again for the reported input, unless the new value works on the app's minSdk.
6.6. The same value (algorithm, curve, protocol, key material) is not now produced through a library or a lower-level API that the checker does not observe: a provider's lightweight API, JNI, a hand-rolled implementation.
6.7. No added method only delegates to the old one.
6.8. The key material no longer comes from the constant the report concerns. Moving or wrapping the constant is not a new source.
6.9. A joined report whose share of the patch is only restructuring has its code left as it was.
6.10. A change that only makes a default explicit touches nothing beyond the reported argument and the statements that build the explicit producer.
Behaviour and compatibility
6.11. Every value that contributed before still contributes (4.8).
6.12. Stored and shipped data still read:
- every reader of a changed stored value is updated in the same patch;
- a value derived from it and stored or compared elsewhere (a hash compared later, a file name) does not change silently;
- ciphertext shipped inside the app under a constant key stays readable: do not remove the key and keep the ciphertext, and do not remove both and lose what the data held.
6.13. TLS:
- the context is not pinned to one version;
- a protocol list you write does not drop a version the negotiating default allowed (TLS 1.3);
- a value you replaced in one API does not still configure another API;
- an "accept all" flag does not still default to true.
- A client whose own connection settings already exclude old protocols gets no extra filter. Where old protocols are really still enabled, filter them on the socket instead of pinning the context.
6.14. A protocol the code implements that mandates an algorithm still uses that algorithm.
6.15. Ciphers and keys:
- a cipher that needs a parameter spec (an IV, GCM parameters) still gets one;
- an encryption init on an AndroidKeyStore key that requires randomized encryption (the default) is not given a caller IV;
- an IV the provider generated is not replaced by one the code chooses.
6.16. No key or trust store is created empty (loaded from null, nothing stored in it) and then used as if it held keys or certificates.
6.17. No two identical statements are left next to each other where the replaced line did something else.
6.18. A digest used as a runtime discriminator is gone, replaced by explicit logic, and every known mapping is kept.
Names and API
6.19. No name still states a behaviour the patch removes: an algorithm, an encoding, a version, or a selector whose branch no longer does what its name says.
6.20. A rename updates every reference (calls, imports, ::references) and every overload of the family. The new name is not already declared, and no renamed call now binds to a different declaration. There is no caller-only rename while the old function still exists.
6.21. No public or protected API was removed or changed while a caller still uses the old form. No new implicitly public Kotlin declaration, and no visibility widened only for a test.
6.22. Every symbol and constructor you call is declared (or added) with that argument count, and declaration scopes match their use. Checked exceptions still propagate or are caught, no catch is left for an exception that is no longer thrown, a replaced sensitive wrapper is disposed of, and no executor task swallows its exceptions.
6.23. Exception messages that tests assert match the messages the code throws.
Tests
6.24. Tests:
- import only declared test libraries and the repository's packages;
- live in the unit-test source set of the changed code's module, in a file named after the class they test;
- call no private members and use no reflection-only seams;
- do not read source files, compare constants, or assert equality on types without equals;
- leave every existing test's expectations unchanged;
- assert the failure cause in tamper tests.
Comments and scope
6.25. No comment was deleted without cause (5.9).
6.26. Every changed production file is in a source set the Android APK compiles. No file outside the plan was changed, and no build file was changed for a test.
Warnings (record them; they never fail a draft)
W1. The diff keeps the user's choices: no user setting or option removed or emptied, each option's check still turning on what it turned on; no value that the caller or the user chose replaced by one the patch picks; the method does not start rejecting values its callers may already pass (a user setting, a stored record, an imported value). A hit becomes a maintainer-choice sentence (10.12); whether it is a regression is decided in 7.6 and 7.8.
W2. A change that keeps a new owner object alive has a dispose test.
W3. A protocol filter you add on a socket has a test of what it filters (4.13).

Stage 7. Behaviour review of your own diff
7.1. Read the whole file, not only the edited block. Follow every caller and every branch the edits change (first run versus existing data, null versus non-null, each flag value) and compare what the code does before and after.
7.2. A regression is a concrete scenario, reachable through the app's own code, in which the patched code now does one of these:
- throws, returns or stores something different;
- skips a side effect it used to perform (creating or writing a file, initialising state);
- accepts or trusts different data.
These are not regressions:
- no longer committing the reported violation (for peers and servers, 3.22 decides);
- a property that follows necessarily from the required replacement value, such as the new algorithm's output length when the value is recomputed and compared within the process, or a file in the app's cache directory, named by the old value, that is no longer found.
7.3. Also not regressions:
- outside actors you would have to invent (another process deleting files mid-call, a server that speaks only an old protocol);
- failure paths the original code already had;
- installing an older version of the app over the patched one;
- the platform behaving against its documentation, unless evidence names such a platform;
- data written in the new form the plan asks for while existing data still reads;
- code the patch leaves doing what it did, such as a joined report the patch does not resolve;
- style, naming, or a speculative risk without a scenario;
- a rename done correctly.
7.4. A value that is persisted, transmitted, compared with a constant, or that names or keys stored data other than a cache stays protected. A changed length, width or key there is a regression.
7.5. A diff that breaks a plan invariant, does what a forbidden change forbids, or does what a concern from stage 3 warns against is a regression; name the scenario. There are two exceptions: a necessary property of the replacement value (7.2), and a concern about no longer accepting something deprecated or insecure, which 3.22 decides. Answer each stage 3 concern with one of: does what it warns against, does not, or only asks someone to verify something this patch does not decide (a device, an endpoint, the checker).
7.6. Where 3.22 shows a dependent, a patch that removes what they rely on, and leaves them no way to keep doing what they did (connecting to their own server, loading their content), is a regression for them; say which kind of evidence it rests on. A patch that keeps them working in another way the evidence supports (the check the app already applies to that peer, a certificate the user supplied) is not. Where an option gates the behaviour, emptying the option is a regression, and so is dropping, in the path the option turns on, anything the option exists to allow, old protocols included.
7.7. Unbounded growth is a regression: a new persistent entry (key store alias, file, preference key, database row) created for each repeated operation (every encryption, save or request), under a name no later operation reuses, and never removed. One entry per stored item, a fixed name reused, or an entry removed together with its data is fine.
7.8. A choice the user makes (a selected option, a setting, an entered value) that now produces something other than what it names or produced before, or an option the patch removes, is a regression. The exception is a replaced value that is itself deprecated or insecure, and that exception never applies in a compatibility path the user turns on deliberately (7.6). A value missing from RVSec's list is not deprecated or insecure for that reason alone.
7.9. Check the patch against constraints the code sets elsewhere: key properties, provider choices, configuration flags. An AndroidKeyStore key generated with randomized encryption required (the default) refuses a caller-supplied IV or nonce at encryption, so every encryption fails, whatever the build says. Adding setRandomizedEncryptionRequired(false) does not change keys already generated.
7.10. Stored data:
- A value stored before the patch that no longer reads is a regression; so is a value read back elsewhere (restore, import, another device) that now depends on something that side lacks. Name the read site.
- So is data written outside preferences (a file, a stream, a database) that the patched code no longer reads.
- When the value comes from user input or an export, a new read path must accept every input the old one accepted: surrounding whitespace, padding, line breaks.
7.11. Every input that contributed to the original result still contributes, unless removing it is the fix (4.8).
7.12. The patch has no effect when RVSec would still see the same calls with the same values. Cases with no effect:
- the restructurings of 4.6;
- a renamed constant holding the same value; a type annotation;
- a different entry point that calls the forbidden API underneath (SSLSocketFactory.getDefault() calls SSLContext.getDefault());
- a factory or wrapper around the same object; an object built and then discarded;
- an access spelled in a form that compiles to the same call (a Kotlin property read and its getter);
- a fallback that reaches the original value again (6.5); the same value through an unobserved API (6.6);
- an object rebuilt from its own parts or re-read from the same store entry; a round trip (6.4); a holder of the app's own with the same parts.
Judge effect by what the reported rule governs at the reported call; changes made for other reports do not count. These do have an effect:
- A call the patch adds on the object or value the reported call then uses (init, load, a setter, nextBytes on the array passed) changes that object's state.
- A forbidden call kept only to find, read, verify or migrate what earlier versions produced, while new data uses an allowed value. Record where the call stays and when it runs. If new data still comes from the kept call's result, the patch has no effect.
7.13. Judge effect for each report of the unit on its own, at its own call and under its own rule. List every report whose share of the patch leaves what its checker sees unchanged. The patch as a whole has no effect only if no report has one.
7.14. Remove edits that serve no report:
- Remove every production edit that resolves neither the reported call nor a joined report and that no other edit needs. An edit is needed when the change depends on it: a caller adapting to a changed signature, or the other half of a shared format or object.
- Remove every test edit that calls nothing the patch changes and checks nothing it produces.
- Keep a test that calls a changed function and asserts a property the new code must keep (equal inputs still match, a round trip still returns its input).
7.15. If the change only replaces a null or omitted argument with an explicit producer of the identical default object, by the documented path, adding no null default to another governed API, mark it as "makes the default explicit". Then it must touch only the reported argument and the statements that build that producer.
7.16. If a maintainer response contradicts a premise behind your invariants, forbidden changes or concerns (what a client, library or platform already does), state the contradiction, quote the response, name the premise, and judge on the response's fact. An edit that exists only because of the contradicted premise is removed.
7.17. A maintainer decision exists only when the patch itself makes a choice among alternatives that the evidence does not settle and only the maintainer can make: which trust store or certificate authorities a new path uses, a format for new data while old data still reads. That goes into the pull request text as one sentence naming the choice and the alternative; it never blocks the change. A concern that only asks for review is not a reason to stop: the maintainer reviews every pull request.
7.18. If the regressions you found show that satisfying the rule would change what the code trusts, accepts or protects, and the original code already uses the API as its documentation intends, record that, with the documented behaviour cited (8.8).
7.19. Give each regression its source. The plan: no draft that follows the plan could avoid the scenario, because it follows from a required edit or an invariant, or because every change that resolves the report does what a forbidden change forbids; name which. The draft: a slip, a step the plan did not ask for, a broken test, a forbidden change another draft could avoid. Whenever you are unsure, say the draft.
7.20. Check each regression found on an earlier draft against this draft, and count it again only if this draft still causes it.

Stage 8. Redraft and replan
8.1. Each plan gets up to three drafts. A draft fails when any item from 6.1 to 6.26 fails, or when stage 7 finds a regression or no effect. Redraft on the same plan, treating each failure as a mandatory requirement. Regenerate only the files the failures name and keep the others as they are, including every declaration the kept files call, with the same name, parameters and static or instance form.
8.2. Replan at most once for the whole unit. The triggers:
(a) Two drafts in a row regressed for a reason the plan causes (7.19): replan now, with those scenarios as constraints that no change may break. A slip of the draft is redrafted on the same plan instead.
(b) The plan's last draft still regresses: replan, with the scenarios as constraints.
(c) Stage 7 found no effect: replan right away, with the reason and the files that receive the value which the old plan left out (4.10). Plan a change the checker sees at the reported call.
(d) The plan's last draft still fails stage 6: replan so that the plan names every declaration and reference to change, keeps visibility as narrow as the callers allow, uses only symbols that exist or that it adds, and really changes the value reaching the reported call.
(e) A reader of the stored value lives in a file outside the plan: replan to include it.
The new plan gets three drafts of its own. If the new plan would change the outcome chosen in stage 3, do not take it: finish the remaining drafts of the first plan.
8.3. If only rename checks fail on the last draft, make one more draft on the non-rename route: add a correctly named function and switch the callers. A rename problem left after that is a note for the reviewer, not a reason to drop the draft.
8.4. Keep as a fallback a draft whose only fault is a comment it deleted; use it if later drafts fail for another reason.
8.5. If a draft's only fault is its new test, keep the draft without that test.
8.6. If the only drafts you can make replace a provider-generated IV with one the code chooses, stop and write NO_ACTION.md as a violation without security impact (3.14).
8.7. After a correct-use judgement (3.35), make one draft only, with no redraft and no replan. If it does not pass stages 6 and 7, write NO_ACTION.md as a violation without security impact.
8.8. When the drafts run out, the outcome is:
(a) every fix would change what the code trusts or protects, and the code is the documented use (7.18): NO_ACTION.md, violation without security impact;
(b) still no effect after the replan, or every draft only hides the call from the checker: NO_ACTION.md, violation without security impact;
(c) the drafts failed only on their own quality (a rename half done, the value left untouched, no edit): NO_ACTION.md, correction not generated, with no issue;
(d) anything else: ISSUE.md if condition (b2) of 3.31 holds, otherwise NO_ACTION.md.
Before you write NO_ACTION.md or ISSUE.md, revert your source edits: restore every edited file to its committed content and delete every file you created.
8.9. Keep track of each draft's failures and their source (plan or draft).

Stage 9. Build
9.1. Once a draft passes stages 6 and 7, build with the build command given at the end of this prompt. It builds the app; it does not run tests.
9.2. If the build fails, decide whether your change caused the failure or it already existed in code you did not touch. Make one repair round:
- Make minimal exact replacements in the files the compiler or the tests point to, and keep behaviour.
- A supporting declaration may change only so that it accepts the new type or arguments.
- Never satisfy the old declaration by rebuilding the old type or value at the call site: that reverses the fix.
- A test file you need that already failed to compile may be fixed minimally.
Then repeat stage 6 on what changed, and stage 7 only if the repair edited a file outside the plan, and build again.
9.3. Propose a pull request only if the build passes. If it still fails because of your change, revert your edits as 8.8 says and write NO_ACTION.md (correction not generated).
9.4. After the build passes, check in the source once more that the reported condition is gone (6.1).

Stage 10. Text
For a pull request (PR.md):
10.1. The title says what the change does, in the imperative, in under 70 characters (for example "Disallow mixed content in the WebViews"). Never "Fix <method>" or "Review requested for ...".
10.2. Write the description in the first person, as the contributor who reviewed this code, in the words a developer of this app would use. Use two or three short plain paragraphs, under 150 words, with no headings, checklists or "Before merging" section, unless the repository's template asks for them.
10.3. Lead with what the code does today. Name the Java API the reported call is on (for example MessageDigest or KeyStore), what RVSec reported about that call, and what the change does to it. Name what the code does with the value as its statements show (what is hashed, encrypted or verified, and from which input), not as a method, field or preference-key name suggests.
10.4. Say in plain words why the value is a problem, as your evidence shows (for example the standard that prohibits it), instead of saying that the rule does not accept it. Refer to the rule, never by its name, only in the sentence saying RVSec found the call. The rule is RVSec's, never the app's own requirement or policy. When the change is made only because RVSec reports the call, say so plainly. Never give a reason your evidence does not support.
10.5. Do not call it a vulnerability unless the impact is confirmed, and do not invent impact.
10.6. Describe only the final diff, including what the build step changed. Refer to code by its location and its source names, never by compiled names (no "-abc1234" suffixes, no constructor or initializer names in angle brackets, no compiler-generated class names). Mention other reports only if the same change resolves them, and say so in one sentence. Never say the change resolves anything else, and do not describe an edit as made for anything else.
10.7. When RVSec's message lists the values it expects, never say it accepts only some of them.
10.8. When the change only makes a default explicit, say that it makes the default explicit and does not change behaviour.
10.9. When the diff writes data in a format earlier versions of the app cannot read, say so in one plain sentence. Add that data from earlier versions still reads only when the diff keeps a reader for it, and never say so otherwise.
10.10. When the diff keeps a forbidden call only to read or migrate data that earlier versions wrote, say in one plain sentence where that call stays, when it runs, and that RVSec still reports it whenever that migration runs.
10.11. State each effect that users, peers or clients will notice as a fact, in one short sentence of your own whose subject is the people who notice it (for example who can no longer connect, and to what).
10.12. When the patch makes a choice the maintainer should weigh (7.17), end with one plain sentence naming the choice and the alternative, in the app's own words.
10.13. Add short notes for what your build could not verify: a device, a server, data from older versions, whether RVSec accepts the change, a naming preference, consumers you could not check. If a name you left unchanged still states the old value, say so in a sentence. If the file was copied from another project, say the fix may belong upstream.
10.14. Say the project builds only if the build ran and passed, and that tests pass only if they ran. Never say the change was tested on a device.
10.15. If the repository has a pull request template, fill in its headings and checklists and tick only what is true. A question about AI use is answered "AI-assisted". Defaults of a review bot that the repository did not configure are not requirements. If the repository's contribution guidelines ask contributors to disclose AI use, add the sentence "AI assistance was used for this contribution."
10.16. Name RVSec as the tool that found the call. Never describe the contribution as automated, generated or produced by a tool chain.

Report on AeSimpleSHA1.SHA1 (MessageDigest), rule MessageDigestSpec
RVSec's record classifies this report as UnsafeAlgorithm, in the rule's constraint section.
Rule source: MessageDigest.crysl — CROSSINGTUD Crypto-API-Rules, Java Cryptographic Architecture rules, https://raw.githubusercontent.com/CROSSINGTUD/Crypto-API-Rules/master/JavaCryptographicArchitecture/src/MessageDigest.crysl
Types it governs: java.security.MessageDigest
Call order it requires: Get · (digest(byte[]) | (update+ · (digest() | digest(byte[], int, int))))+
Events it matches:
- Get: Observed when a getInstance(String) or getInstance(String, provider) call is resolved to java.security.MessageDigest. It satisfies the rule's Get event only when the selected algorithm argument satisfies the rule predicate exactly: algorithm in {"SHA-256", "SHA-384", "SHA-512"}. Observing a factory call alone does not establish that predicate, especially when the argument is not statically known. Call shapes: `MessageDigest.getInstance(`, `java.security.MessageDigest.getInstance(`.
- Update: Observed only when the receiver is resolved to java.security.MessageDigest and the overload is update(byte), update(byte[]), update(byte[], int, int), or update(ByteBuffer). It contributes to a conforming path only after Get and only when followed by a modeled Digest event. For update(byte[], offset, len), the rule predicate additionally requires length[input] >= offset + len, offset >= 0, and len > 0; merely calling update does not prove those conditions. Call shapes: `.update(`, `messageDigest.update(`.
- DigestWithInput: Observed when digest(byte[]) is invoked on a java.security.MessageDigest receiver. It satisfies the digest-with-input branch only after Get; this branch is permitted without a prior explicit update because the JDK API documents digest(byte[]) as a final update followed by completion. Observing this call does not establish any property of the input's contents or the returned digest's later use. Call shapes: `.digest(`, `messageDigest.digest(`.
- DigestAfterUpdate: Observed when digest() or digest(byte[], int, int) is invoked on a java.security.MessageDigest receiver. It satisfies the update-then-digest branch only after one or more modeled Update events following Get. For digest(output, offset, len), the rule additionally requires length[output] >= offset + len, offset >= 0, and len > 0; seeing the call does not itself establish these bounds. Call shapes: `.digest(`, `messageDigest.digest(`.
What RVSec checks under this rule: For a modeled java.security.MessageDigest acquisition, an explicit message such as "expecting one of {SHA-256, SHA-384, SHA-512} but found SHA-1" indicates that the detector associated the factory algorithm argument with SHA-1 and that value violates this CrySL rule's algorithm-membership predicate.
Requirements the rule states:
- The relevant call target is java.security.MessageDigest.getInstance(String) or java.security.MessageDigest.getInstance(String, ...).
- algorithm in {"SHA-256", "SHA-384", "SHA-512"}.
- For update(byte[], preOffset, preLen): length[preInput] >= preOffset + preLen, preOffset >= 0, and preLen > 0.
- For digest(output, offset, len): length[output] >= offset + len, offset >= 0, and len > 0.
- The modeled event sequence conforms to Get followed by one or more permitted digest-computation branches.
Limits of the check, recorded with the rule:
- The supplied findings show constraint messages, not a complete event trace, receiver type-resolution trace, or proof of runtime reachability.
- The rule itself does not define why this exact three-algorithm policy was chosen, nor does it classify the purpose of a digest.
- The source rule does not state how a particular scanner reports unresolved values; therefore the meaning of a finding whose message is only "unknown" cannot be determined from the rule file alone.
- This source was verified at the repository's master branch; the exact CrySL rule revision bundled with the detector was not supplied.
Violations of this rule without a security stake, recorded with the rule (3.15):
- MD5 or SHA-1 used only as a non-adversarial cache-file key, in-memory hashCode helper, checksum, or UI/display fingerprint. Such code still violates the rule's unconditional allow-list, but may not represent a security defect in context.
Possible false-positive shapes listed with the rule, never reviewed against it; they never support a dismissal (3.15):
- Algorithm values selected dynamically where static analysis reports an unresolved or overly broad value set although production configuration restricts the value to an allowed algorithm.
- A report tied to a source location that contains multiple digest-related calls, without enough supplied trace information to identify which java.security.MessageDigest factory invocation supplied the constrained algorithm.
- A zero-length update(byte[], offset, len) or digest(byte[], offset, len) operation that is valid for the runtime API but violates the CrySL rule's explicit len > 0 predicate.
- Code using digest(byte[]) directly after getInstance. This is permitted by the verified CrySL protocol and should not be inferred to be an incomplete-update violation merely because no separate update call appears.

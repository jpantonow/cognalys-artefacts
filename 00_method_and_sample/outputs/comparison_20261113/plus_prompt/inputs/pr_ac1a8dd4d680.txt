Report on CryptoManager.getOrCreateKey (KeyStore), rule KeyStoreSpec
RVSec's record classifies this report as InvalidSequenceOfMethodCalls, in the rule's order section.
Rule source: KeyStore.crysl in CROSSINGTUD/Crypto-API-Rules, https://raw.githubusercontent.com/CROSSINGTUD/Crypto-API-Rules/refs/heads/master/JavaCryptographicArchitecture/src/KeyStore.crysl
Types it governs: java.security.KeyStore
Call order it requires: Get, Load, ((GetEntry?, GetKey) | (SetEntry, Store))*
Events it matches:
- Get: Observed when source/type resolution identifies java.security.KeyStore.getInstance(String) or java.security.KeyStore.getInstance(String, provider). It satisfies only the Get event; it does not establish that a provider supports the type, that the type passes the CrySL whitelist, or that the returned object was successfully used. Call shapes: `KeyStore.getInstance(`, `java.security.KeyStore.getInstance(`.
- Load: Observed when a resolved java.security.KeyStore receiver invokes load(InputStream, char[]) or load(KeyStore.LoadStoreParameter). It is protocol-valid only after Get on the same tracked KeyStore object. Observing the call does not prove normal return, successful integrity verification, successful unlocking, or that the keystore contents are trustworthy. Call shapes: `.load(`.
- GetEntry: Observed when a resolved java.security.KeyStore receiver invokes getEntry(String, KeyStore.ProtectionParameter). It is allowed only in the read branch immediately before GetKey, after Load, on the same tracked object. The call alone does not prove that an entry exists, is recoverable, or has an expected Entry subtype. Call shapes: `.getEntry(`.
- GetKey: Observed when a resolved java.security.KeyStore receiver invokes getKey(String, char[]) and its result is modeled as the rule variable key. It is protocol-valid only after Load, optionally preceded by GetEntry in that repetition. The call does not prove that the result is non-null, that password recovery succeeded, or that the returned Key is private, public, or secret. Call shapes: `.getKey(`.
- SetEntry: Observed when a resolved java.security.KeyStore receiver invokes setEntry(String, KeyStore.Entry, KeyStore.ProtectionParameter). It is protocol-valid only after Load and must be followed by Store within the modeled write branch. Observing it does not prove that the provider applied effective confidentiality or protection to the entry. Call shapes: `.setEntry(`.
- Store: Observed when a resolved java.security.KeyStore receiver invokes store(KeyStore.LoadStoreParameter) or store(OutputStream, char[]). It is protocol-valid in this rule only after SetEntry in the modeled write branch. Observing it does not prove successful persistence, durability, integrity protection, or that the output destination is access-controlled. Call shapes: `.store(`.
What RVSec checks under this rule: For a tracked java.security.KeyStore object, accepted use begins with a modeled getInstance overload and load overload, then repeats either an optional getEntry followed by getKey or setEntry followed by store. The type argument must be one of JCEKS, JKS, DKS, PKCS11, or PKCS12; passwordIn, passwordOut, and passwordKey must never be String-typed; passwordIn must not be hard-coded.
Requirements the rule states:
- generatedKeyStore[this] after Load
- generatedKey[key, _]
- generatedPrivkey[key]
- generatedPubkey[key]
Limits of the check, recorded with the rule:
- The raw rule does not model getInstance(File, char[]) or getInstance(File, KeyStore.LoadStoreParameter), even though these APIs return an already-loaded KeyStore.
- The rule does not list setKeyEntry, setCertificateEntry, deleteEntry, aliases, containsAlias, or other documented KeyStore methods.
- The rule's source does not identify a fixed detector release, configuration, classpath, Android API level, or provider implementation; behavior for unresolved calls and interprocedural flows depends on the detector implementation.
- The CrySL source is referenced at the mutable master branch rather than an immutable commit.
Violations of this rule without a security stake, recorded with the rule (3.15):
- Android application code that reads a secret key with KeyStore.getEntry(alias, null) and KeyStore.SecretKeyEntry.getSecretKey() (or reads the same entry again with getEntry) instead of getKey(alias, password): the rule's read branch (GetEntry?, GetKey) admits getEntry only immediately before getKey, so the documented Android idiom leaves the automaton and is reported as an invalid call sequence. Both calls are read-only and return the same key from the Android keystore; no security property depends on their order. This shape covers only such reads; a sequence involving setEntry, store, or a missing load is not covered.
Possible false-positive shapes listed with the rule, never reviewed against it; they never support a dismissal (3.15):
- Android application code using java.security.KeyStore.getInstance("AndroidKeyStore") where the static rule's five-value type whitelist is applied literally.
- Android or provider-integrated code using "AndroidCAStore" or "BKS", which are absent from the raw rule's type whitelist.
- Code using KeyStore.getInstance(File, char[]) or KeyStore.getInstance(File, KeyStore.LoadStoreParameter), whose documented behavior returns an already-loaded KeyStore but whose overloads are absent from the rule.
- Valid code using documented setKeyEntry(...) or setCertificateEntry(...) instead of the rule's modeled setEntry(...).
- Android application code that calls setEntry(...) on a KeyStore obtained with getInstance("AndroidKeyStore") without a following store(...): the Android keystore service persists an entry when it is set, and AndroidKeyStoreSpi.engineStore throws UnsupportedOperationException, so the rule's Store after SetEntry is neither needed nor possible.
- A char[] password assembled from a literal, configuration default, resource, wrapper, callback, or native boundary where the detector's notHardCoded/data-flow approximation does not reflect the deployed secret-management controls.
- Kotlin delegated properties, wrapper methods, reflection, or dependency injection that obscure the exact java.security.KeyStore receiver, overload, object identity, or call order.
